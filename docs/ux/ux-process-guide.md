# 🧭 前端 PoC 完整开发流程（详细版 · UX Process Guide）

以下流程描述「预览 → 状态判断 → UAT → 设计 → 开发 → 回归」的完整闭环，  
是本 PoC 的核心 UX/前端联动开发规范。

---

## **STEP 1：预览页面（Preview the Current State）**

目的：查看当前界面的真实渲染情况。

执行内容：
- 打开 `npm run dev`
- 浏览首页、弹窗、侧栏、对话区、输入区
- 将观察到的问题以简短 bullet points 记录

输出示例：
- “访客弹窗按钮对齐不一致”
- “推荐卡片行距偏大”
- “输入框禁用状态缺样式”

---

## **STEP 2：状态评价（State Review）**

目的：判断当前界面属于 S1~S8 中的哪一个状态，并检查是否符合状态定义。

执行内容：
- 对照 `ux-flow-and-states.md`
- 分析当前界面与状态的匹配程度
- 标记“符合 / 不符合”

输出物：
- 一份该状态的评价结果（简表即可）

---

## **STEP 3：轻量 UAT（Mini-UAT）**

目的：快速验证该状态的功能是否符合核心用例。

示例：
- S1：首次无访客 → 是否弹窗？
- S2：空会话 → 是否进入欢迎页？
- S3：输入为空 → 是否禁用发送按钮？
- S4：消息发送 → 是否出现 Loading skeleton？

输出物：
- 每个用例的“通过/不通过”与原因记录

---

## **STEP 4：问题整理 → 形成设计 Prompt（Design → Code Pipeline）**

目的：在写代码之前确保 UI/交互方案清晰统一。

执行内容：
- 将 UI/交互问题整理成准确的列表
- 编写 prompt 给 Figma 或 MasterGo

输出物：
- 一段描述清晰的设计 prompt
- 更新后的 UI（线框或视觉稿）

示例问题清单：
- 字段顺序需调整为：昵称 → 加入时间 → 访客ID
- 弹窗水平对齐不一致
- 底部按钮与内容间距不足

---

## **STEP 5：代码补充（Development via Codex with Strict Boundaries）**

目的：基于设计稿补齐 UI 与逻辑，实现指定状态的改进。

执行内容：
- 明确修改范围（如仅限某组件文件）
- 编写 Boundaries 清晰的 Codex prompt
- 实施小范围修正（UI / 状态逻辑）

规则：
- 不修改未指定的文件
- 不新增状态外的逻辑
- 所有改动必须与设计一致

输出物：
- 更新的 React/Tailwind 代码
- Codex 自动输出的变更摘要

---

## **STEP 6：回归 UAT（Regression UAT）**

目的：确保代码改动满足状态需求，且未破坏其他功能。

执行内容：
- 再跑一次当前状态的全部用例
- 检查相邻状态是否正常（例如 S2/S3 不受影响）

输出物：
- “状态 Sx 已完成”的验证结果

---

## **STEP 7：进入下一个状态（Iterate by States）**

流程：
S1 → S2 → S3 → S4 → S5 → S6 → S7 → S8

每完成一个状态：
- 勾选 project-plan 的对应任务
- 完成 UAT  
- 如需，记录 change-log

---

# ✔️ 流程总结

通过“预览 → 状态评价 → UAT → 设计 → 实现 → 回归”六步循环，  
PoC 将具备：

- 稳定性  
- 可控性  
- 可评审性  
- 可复盘性  
- 可快速演示  

这是本 PoC 的核心 UX/前端协作模式。



# 前端 PoC 开发流程指南（UX Process Guide · v0.1）

本文档定义港股市场信息助手 PoC 的前端开发方式、状态驱动验收方法（UAT），以及设计→代码的协作流程，用于确保 PoC 的一致性、可控性与可验证性。

该文档与以下文件共同构成 PoC 的前端规范体系：
- `docs/ux/ux-flow-and-states.md` —— 定义全部 8 个 UX 状态
- `docs/ux/ux-uat-checklist.md`—— UAT 检查表
- `project-plan.md` —— 迭代计划与任务落地

---

## 1. 整体流程（状态驱动 · State-Driven Development）

前端 PoC 的落地流程遵循以下顺序：

**1. 状态模型（ux-flow-and-states） →  
2. 代码现状盘点 →  
3. 一状态一验收（UAT） →  
4. 缺的状态先设计（Figma/MasterGo） →  
5. 设计通过后导出代码 →  
6. Codex 在限定范围内重构/补全 →  
7. 再通过该状态的 UAT**

该方法可避免 PoC 出现“代码越写越散”“AI 自动生成但无规格可依”的问题。

---

## 2. 在 project-plan 中的落地方式

### 2.1 新增章节：前端状态落地进度

`project-plan.md` 中建议加入如下章节：

```md
## 前端状态落地进度（按 UX 状态拆分）
> 对应文件：docs/ux/ux-flow-and-states.md
每个状态由「现状 → 待办 → UAT」三部分组成。

示例：状态 1「首次访问态」
md
复制代码
### 状态 1：首次访问态（First Visit / Visitor Init）

- 对应 UX 文档章节：3.1  
- 目标：首次进入页面时，若无访客信息，则弹出访客引导弹窗并生成 guestId、joinDate。

#### 现状评估
- [x] 基本逻辑已实现（localStorage / guestId 生成）
- [ ] 样式与设计稿不一致（深蓝版未对齐）
- [ ] 清除数据后的回归路径需验证

#### 待办（Dev）
- [ ] 更新访客弹窗样式
- [ ] 确认「清除所有数据」后能正确触发首次访问态

#### UAT 用例
- 用例 1：无访客信息 → 弹出引导弹窗  
- 用例 2：已有访客信息 → 不弹出弹窗  
- 用例 3：点击清除数据 → 刷新后再次出现弹窗
所有其他状态（首页态、输入态、对话态、错误态、合规态、场景态、会话管理态）依此格式编写。
```

### 2.2 代码开发节奏：严格限定范围（Boundary Control）

每次开发前应明确三个点：

```md
#### 今日前端目标（示例）

- 修改范围：仅限 `src/components/chat/modals/` 与 `src/utils/guest.ts`
- 今日目标：让「首次访问态」的 3 个 UAT 全部通过
- 不做内容：不修改 messages、scenarioKey、会话列表等逻辑
```

Codex prompt 也必须围绕这三个内容，限定操作范围，使得修改可预测、可验证。

---

## 3. 设计→代码 的引入流程（PoC 简化版）

在状态未实现或 UI 不够清晰时，使用以下流程：

1. 在 Figma / MasterGo 中基于状态设计对应页面态/组件（线框或视觉稿均可）。  
2. 自己检查视觉/交互，判断“可用于 PoC 演示”即可（无需像正式设计系统一样细致）。  
3. 导出代码到：`design/design-exports/`。  
4. 将导出代码作为参考，由 Codex 在 `src/components/chat/...` 中按结构整合，避免完全覆盖。  
5. 实现后必须跑对应的 UAT 用例 → 通过才算完成该状态。

这样未来可升级到完整的“设计验证循环”（Prompt→Design→Code→回归），无需推倒重来。

## 4. UAT 流程（简化但有效）

可以采用两种 UAT 方式：

**方式 A：项目内创建 UAT 检查表（推荐）**  
文件位置：

```bash
docs/ux/ux-uat-checklist.md
```

内容示例：

```md
# UX UAT 检查表（PoC v0.1）

| 状态编号 | 状态名称           | 用例                                   | 结果 |
|----------|--------------------|----------------------------------------|------|
| S1       | 首次访问态        | 无访客信息 → 弹窗                      | ☐    |
| S2       | 首页默认态        | 无会话 → 展示欢迎页面 + 推荐卡片      | ☐    |
| S4       | 对话态            | 发送消息 → AI 回复出现                 | ☐    |
| S5       | 错误态            | 强制接口失败 → 显示错误提示条         | ☐    |
| S6       | 合规警告态        | 输入敏感词 → 显示黄色警告条           | ☐    |
| S7       | 场景态            | 点击推荐卡片 → 填入示例问题           | ☐    |
| S8       | 会话管理态        | 切换会话 → 加载对应消息               | ☐    |
```

**方式 B：使用 Excel**  
你也可以在 `/requirements/` 下自行维护 Excel 检查表。

---

## 5. 总结：PoC 的前端开发原则

- 所有行为必须对应到一个明确的 UX 状态  
- 所有代码修改必须通过该状态的 UAT  
- 所有未明确的 UI 必须先用 Figma/MasterGo 生成  
- 所有设计产物必须通过 Codex 以指定范围整合，而不是无序生成  
- 开发节奏以“状态”为单位，而不是以“组件”或“文件”为单位  

只要坚持这套模型，PoC 会越做越稳，之后扩展设计系统、接入真实 API、做深度交互都不会出现结构性返工。
